# RA 流水线 S1/S2/S3 优化机会（2026-09-17，全数据实测）

> 结论先行：**当前瓶颈不是"生成得不够多"，而是"生成的东西注定过不了闸"。**
> 全库 19,567 条表达式里 **89.7% 从未被回测**，而已回测的那些只有 14.8% 过 1Y 闸 / 11.8% 过 2Y 闸 /
> 31.1% 过 PROD 闸。继续加 S2 吞吐只会加深积压。**优化重心应放在"提高单位回测的过闸概率"与"止住规则泄漏"。**

## 1. S1（字段扫描/理解）：缺口是"硬前置没落地"

### 1.1 ★★★ 25% 的白名单数据集**根本没有 catalog** → 整条腿跑不起来

`gate.py::load_whitelist` 找不到 catalog 会直接 `raise FileNotFoundError`（实测 JPN/`news_sentiment_nlp` 即如此）。
实调解析器（含 DB catalog + 两种文件兜底）测 93 个白名单数据集：

| 区域 | 白名单 | **缺 catalog** |
|---|---|---|
| **JPN** | 12 | **10** |
| GBR | 11 | 6 |
| ASI | 8 | 6 |
| CHN | 3 | 1 |
| 其余 8 区（DEU/EUR/GLB/HKG/IND/KOR/MEA/USA） | 59 | 0 |
| **合计** | **93** | **23（25%）** |

**这直接解释了 JPN 的断链**：漏斗显示 JPN「门禁放行 268 条 → 回测完成 **0 条**」——
因为 12 个白名单数据集里 10 个连门禁都进不去。

**改法**：把 catalog 缺口纳入与体检包同级的**开区硬前置**（我上轮给体检包加了 `--inspect-mode {warn,enforce}`，
catalog 目前**没有任何机械检查**）。最小实现：在 `wave_gate.py` 开波前置里加一次
`load_whitelist()` 探活，缺失即按 mode 告警/拦截。

### 1.2 体检包与 catalog 是"两道开区前置"，但只有一道有闸
体检包覆盖 7 区（本地 WebData 快照边界，见 §批2.5）；catalog 缺口 25%。两者都属"缺了就没法挖"，
却都没有 fail-closed 默认。**建议统一成一份"开区前置清单"并默认 enforce。**

## 2. S2（生成）：**这里有一处规则泄漏，是当前最大的单点浪费**

### 2.1 ★★★ 闸5「禁加权混合」拦住的比例远低于应拦

用户定案：**禁一切加权混合**（2026-09-13 路线 A，09-16 重申）。实测（**2026-09-17 复测修订**）：

- 真·加权混合（**任一** `add(` 的顶层实参 ≥2 个以「系数*」开头 —— 括号平衡扫描，含嵌套）= **1,547 条**（占全库 7.0%）
- 抽样 220 条送**真闸**校验：**只 block 41 条（19%），漏 179 条（81%）**

> ⚠ **口径修订记录**：本报告初版用"**顶层** `add`"作判定，得 872 条 / 漏 72%。
> 复测发现该判定器**漏掉了嵌套形态**（如 `quantile(add(multiply(0.7,X), multiply(0.3,Y)))` —— 这正是 GEM 的真实产出形态），
> 故正确口径为「任一 `add(`」→ 1,547 条 / 漏 **81%**。**结论方向不变且更严重**。

**根因（已用最小用例隔离）**：`weighted_signal_mix` 正则要求**两条腿都**紧跟
`(rank|zscore|ts_rank|group_rank|normalize|scale)`：

| 形态 | 闸5 |
|---|---|
| `add(0.4*rank(a), 0.6*rank(b))` | BLOCK ✅ |
| `add(0.4*rank(a), 0.6*subtract(0, rank(b)))` | **放行 ★** |
| `add(0.4*subtract(0, rank(a)), 0.6*rank(b))` | **放行 ★** |
| `add(0.4*subtract(0, rank(a)), 0.6*subtract(0, rank(b)))` | **放行 ★** |
| `add(multiply(0.4, rank(a)), multiply(0.6, subtract(0, rank(b))))` | BLOCK ✅ |

即：**`multiply()` 函数式两条规则是形状无关的（宽），星号中缀那条把操作符写死了（窄）**。
而真实语料里主流形态恰恰是 `coef * subtract(0, rank(x))`（做差/镜像腿），于是整类漏网。

**改法**：把 `weighted_signal_mix` 从「正则匹配两个加权项」改成
**「顶层 `add(` 且括号平衡切分后 ≥2 个参数以「数字*」开头」**——我已在验证脚本里写好该判定器，
可直接移植为 `gate.py` 的结构判定（不再依赖正则）。

### 2.2 ★★ 窗口白名单**只存在于散文里，且工具默认值与之冲突**

SOP 两处（`wq-brain-ra-pipeline` 步 4、`brain-make-some-gem`）都写"只用 **1/5/22/66/252/504/1008/1260**"，
但**没有任何机械守护**。实测 19,567 条里 **4,491 条（23.0%）**用了非白名单窗口：

| 违规窗口 | 次数 | 来源 |
|---|---|---|
| **20** | 1,402 | ← `_DEFAULT_WINDOWS` |
| **10** | 1,389 | ← `_DEFAULT_WINDOWS` |
| **120** | 478 | ← `_DEFAULT_WINDOWS` |
| 60 | 413 | ← `_DEFAULT_WINDOWS` |
| 44 / 126 / 21 / 2 / 250 / 315 | 361/304/285/182/148/148 | 其他 |

**因果链很清楚**：`operator_coverage.py::_DEFAULT_WINDOWS = [20, 60, 120, 5, 10, 252]`
——**6 个默认值里 4 个不在白名单内**（20/60/120/10），且这些默认值被用来实例化 window 占位符。
**工具默认值就是污染源。**

**改法**：① 把 `_DEFAULT_WINDOWS` 对齐到 SOP 白名单；② 把窗口白名单做成 gate 的**机械规则**（现在全靠自觉）。

### 2.3 ★ 同族自相残杀应前移到生成期
`alphas.self_correlation` 均值 0.433、**最大 0.9445**。SOP 已明确"同波兄弟变体=同族，SELF 0.9+"，
但目前是在 **S6 才发现**。建议 S2 生成后、S3 提交前加一道**骨架去重**（骨架签名 + 主字段），
把撞车挡在烧配额之前。

### 2.4 `quantile` 占 13.4%（2,624 条）——ARITY 高频错误源
历史上闸4 ARITY 命中 312 次。虽已有闸兜底，但建议在 GEM 生成 prompt 里前置注入正确 arity。
**优先级低于 2.1/2.2。**

## 3. S3（回测）：第一优化不是"跑更多"，而是"止漏 + 补测"

### 3.1 ★★★ `prod_corr` 只测了 6.7% —— SOP 的"最省算力一招"没有落地
SOP（USA 提示词 + profile）把 **prod-first** 称为"USA 命门，省算力最多的一招：每槽先 1–2 条骨架查
`prod_corr`，≥0.6 立即停扩换腿"。实测：

- `alphas` 4,038 行，**只有 270 行（6.7%）有 `prod_correlation`**
- 全表扫描：`prod_correlation` 只存在于 `alphas` 一列；`backtest_results` **完全没有相关性列**
- `backtest_results.payload_json` 抽样 400 条，含 prod_corr 字段 = **0**
- ledger 里与 prod 相关的键只有 **7 个手写条目**（`wave143_prod_wall`、`prod_saturation_event_20260914`…）→ 全是**事后记的教训，不是过程测量**

**结论**：prod_corr 没有系统性、可查询的过程记录 → 0.6 预警线**没有数据可供触发**。
结合 §0 的均值 0.767，等于"我们没在看这道闸，而它正好是杀我们最多的一道"。

**改法**：S3 每槽按约定抽样 1–2 条测 prod_corr 并**落库**（`backtest_results` 加列或
`alphas.prod_correlation` 及时回填），让预警线真正可触发。这是**投入最小、收益最大**的一项。

### 3.2 ★★★ 385 个波 / 6,311 条表达式（32%）**从未过门禁**
`LEFT JOIN gate_results` 实测：**6,311 条表达式所在的 385 个波没有 gate_results 记录**。
Top：`JPN/s2_intraday_pv_feats_d1` 517 条、`USA/s2_multifactor_return_pred_d1` 336 条、
`EUR/s2_pattern_scores_d1` 179 条。

这些表达式**永远无法合法进入回测**（门禁断链）。这也是我之前给 `wave_gate.py` 加
"开波闸下沉"要解决的问题之一，但那管的是**新波**；**存量 385 波需要一个补门禁/废弃的裁决流程**
（工具已提示：`tools/wave_gate.py --wave <W>` 补门禁，或标 `dropped`）。

### 3.3 积压闸目前是灰度 warn，真实积压已 89.7%
我上轮把 `backlog_gate` 的 `unconsumed_ratio_max=0.30` 落地为**灰度（`unconsumed_enforce=False`）**，
USA 实测 90% 溢出只打 `[灰度·未拦截]`。**现在数据已证明积压不是偶发而是常态（89.7%）**，
可以考虑对**至少部分区**切 `enforce`，或先按区给出"先消化"的排期。

## 4. 建议优先级（按 ROI 排序）

| # | 动作 | 预期收益 | 成本 | 风险 |
|---|---|---|---|---|
| **1** | **修 `weighted_signal_mix` 为结构判定**（§2.1） | 堵住 72% 的禁用形态泄漏，直接提升过闸率与防过拟合 | 小（判定器已写好） | 收紧门槛 → 存量批次可能被判 FAIL，需灰度 |
| **2** | **prod_corr 抽样落库**（§3.1） | 让 SOP 的"最省算力一招"真正可触发；均值 0.767 的根因治理 | 小–中（加列/回填 + S3 调用点） | 低 |
| **3** | **catalog 开区前置 fail-closed**（§1.1） | 解开 JPN（10/12）、GBR（6/11）、ASI（6/8）的整腿停摆 | 小（复用 `--inspect-mode` 模式） | 低（缺就该拦） |
| **4** | **`_DEFAULT_WINDOWS` 对齐白名单 + 窗口规则机械化**（§2.2） | 消掉 23% 违规窗口的**产生源** | 很小 | 低 |
| **5** | **存量 385 波补门禁/废弃裁决**（§3.2） | 释放 6,311 条卡死表达式 | 中（批处理 + 逐波裁决） | 中（需谨慎，别误废） |
| **6** | **S2 生成期骨架去重**（§2.3） | 减少 SELF 自残（最高 0.9445） | 中 | 低 |
| **7** | 积压闸按区切 `enforce`（§3.3） | 止住 89.7% 继续膨胀 | 小 | **高**（会停波，须按区决策） |

**不建议做**：继续加大 S2 生成吞吐。当前 89.7% 未消化、32% 未过门禁，
**再生成只会加深积压**；先修 1–4，再谈铺量。

## 5. 一句话总结
**S2 的规则没有真正执行（加权混合漏 72%、窗口白名单只写在散文里且工具默认值与之冲突），
S3 的关键测量没有落库（prod_corr 仅 6.7%），S1 的硬前置没有闸（catalog 缺 25%）。**
三者叠加，产出的东西平均就贴着 PROD 红线（均值 0.767）——**这不是"挖得不够多"，是"选得不够准"。**
