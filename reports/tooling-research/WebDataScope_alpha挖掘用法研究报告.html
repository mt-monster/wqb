一、项目是什么

WebDataScope 是一个 WorldQuant BRAIN 平台浏览器扩展（Chrome/Edge）。它由两部分构成：① 离线数据包（zlib+msgpack 编码，导入 IndexedDB，供零成本预筛）和 ② 浏览器增强脚本（在平台页面注入，提供实时标记、分析、稳定性增强）。对 Alpha 挖掘最有价值的是离线数据包——它把"社区用数千/数十万次提交踩出来的教训"沉淀成可离线查询的质量先验。

二、核心：字段筛选逻辑（三层漏斗）

这是你问的重点。字段筛选不是靠"字段名好不好听"，而是三层漏斗：先用社区验证先验过滤「有没有人挖出过好结果」，再用数据体检判断「这个字段适不适合做信号」，最后用中性化匹配确定「在哪个中性化下最优」。数据包的字段体检数据只在部分组合有（160 个），因此第一层是全局可用的一层。

第 1 层：社区验证先验（isos.datafield）

数据包的 isos.datafield[<field>] 给出每个字段的社区提交 count/sharpe/fitness。这是"极少有人提交的字段=低质量"的量化版。核心逻辑：

字段 countsharpe判定动作
100–3000≥ 1.1×区域均值甜点区已验证可提交、未饱和优先入围（ProdCorr 死区风险低）
> 30000任意饱和模板空间被社区挖穿需高度非对称结构才能过 ProdCorr<0.7，冷启动避开
> 30000低（< 均值）踩坑社区大量尝试仍失败避免作主信号（如 sharesout 40243 次 / sharpe 0.219）
< 50任意未验证质量风险高默认跳过；仅作刻意去相关的探索
💡
字段级最优中性化同样来自这里：neutralization.datafield[<field>]，取 count≥20 且 osis_count≥20 中 sharpe 最高的前 2–3 个，排进模拟计划前列。

第 2 层：数据体检（字段 .bin，决定预处理算子）

有体检数据的字段，进一步用 10 年统计决定"怎么用"。这是字段筛选里最容易忽略、却最能提升挖掘命中率的一层：

观测指标判定结论 / 动作
CoverageRatio 均值< 0.4必须 backfill否则 CONCENTRATED_WEIGHT；回测注意早年失真
Coverage 厂字形（早低近高）近年 > 早年×1.3数据商中途扩容，稳健性判定用近 3 年
IndicativePositive/NegRatio≈ 1（单边）勿用原始水平做多空，先变化率/排名/与基准差
yearly_distribution 形状spread最佳可直接用或轻度预处理
同上zero_inflated（[0,0.1)>50%）事件/稀疏字段，配 ts_backfill 或事件门控（trade_when）
同上ceiling（[0.9,1]>50%）值截尾，winsorize/rank 抑制
同上point_mass/concentrated有效信息少，慎作主信号；作辅助/门控
skenewss 均值> 2外层 rank/signed_power(x,<1)/winsorize 抑制极值
kurtosis 均值> 8（厚尾）外层 rank/signed_power(x,0.5)，避免直接 ts_mean
IntegerStatus= 1（离散）优先 rank/bucket/group_rank，慎用平滑算子和 ts_delta
frequencymonthly / quarterly时序窗口 ≥ 更新周期（月度≥21d，季度≥63d），短窗只采样噪声
LongCount/ShortCount严重失衡必须对称化（signed_power/双序 rank/减均值），否则单边持仓
🛠
字段组合建议（分布形状配对）：point_mass/zero_inflated（稀疏事件）作门控 + spread（连续）作主信号 → trade_when(gating_cond, signal_expr, -1)；两个 spread 双 rank 去相关 → rank(a)-rank(b)；ceiling+zero_inflated 互补 → 降低结构相关性。

第 3 层：中性化匹配（osis_count 可信度门槛）

每个字段/数据集在每种中性化下都有 {count, sharpe, osis_count, fitness}。osis_count 是 OS 子集样本量，比纯 IS count 更可信——这是"中性化推荐可信度"的关键。三级门槛：

门槛判定用法
高可信count≥20 且 osis_count≥20直接作为该字段/数据集的推荐中性化
中可信count≥5（osis 未验证）字段级中性化推荐，用 sharpe 排序但标注 osis 覆盖
低可信osis_count 远小于 count大部分提交尚无 OS 数据，推荐打折；优先参考类别级
⚠️
反例：neutralization.dataset[analyst10] 中 NONE(2次) 的 sharpe=1.069 但 osis_count=1 → 不可信；INDUSTRY(322次, osis 307) 才是可靠推荐。切勿被低样本高 sharpe 误导。

三、除已知用法外，新发掘的 6 大用法

你已知数据质量、字段选择、中性化选择。以下是从浏览器增强脚本中挖掘出的、尚未沉淀进现有工具链的用法：

1. 算子使用画像 → 差异化 / 拥挤度预判（genius.js: opsAna）

genius.js 的算子分析统计你自己提交的 REGULAR alpha 中每个算子的使用频率（按天取前 4 个，避免单日刷量扭曲）。用途不限于自我回顾：

  • 冷门算子机会：表格中 count=0 的算子（nonZeroCount 之外的）是社区几乎没用的算子 → 用它做差异化结构，可显著降低 ProdCorr（与大家用同一批算子=结构同质化）。
  • 拥挤算子预警：自己提交集中用的算子，往往是社区通用算子（如 rank/ts_mean），高用量提示结构同质 → 换更冷门的等价算子。
  • 算子级多样性追踪：可与项目记忆的"每 10 次回测做多样性评估"联动，补充算子维度的探索率。

2. 个人技术分布热力图 → 空白领域挖掘（distribution.js）

distribution.js 调用 /users/self/activities/diversity?grouping=region,delay,dataCategory，把你自己在 region × 数据类别 的 alpha 数量画成散点热力图，并标注每个格子的 dataDiversity.check（是否通过多样性要求）。用途：

  • 个人空白领域：散点上没有点或点很小的 region×类别 = 你完全没碰过的领域 → 多样性机会（也往往竞争压力更小）。
  • 多样性合规：check 非 PASS 的格子说明该领域已过度集中，需主动分散到其他 region/类别。
  • 投入产出再平衡：把算力从"已饱和的自家强项"（点很大）挪到"空白高潜力"格子。

3. ProdMemo 本地相关性库 → 历史 ProdCorr 复用 & 拥挤度反推（prodmemo.js）

prodmemo.js 自动把每个查看过的 alpha 的 PC（ProdCorr）/ PPC（PoolProdCorr）/ SC（SelfCorr）最大值缓存到本地（WQP_ProdMemo_*，可导出 JSON）。用途：

  • 避免重复回测已知高相关的组合：新候选在模拟前，先查同数据集/同字段的历史 alpha 的 PC——若已有一堆 PC>0.7，说明该方向拥挤，直接换。
  • 拥挤度反推：如果自己某数据集/字段的多个候选 PC 都高，反推该区域被社区挖穿的概率高。
  • ProdCorr 演化追踪：配合 updated 时间戳，看同一 alpha 的 PC 是否随时间上升（市场饱和信号）。

4. 回测稳定性增强 → 长跑不中断（noMoreDifficulties.js + simulate.js）

这两个脚本解决"回测被平台网络/配额打断"的痛点，直接提升长批量挖掘效率：

脚本机制折算的挖掘价值
noMoreDifficulties.js对 GET api.worldquantbrain.com/* 自动重试（429/500/502/503/504，最多 10 次，线性退避 retry×500ms），网络错误 "Failed to fetch" 也重试批量回测 / 查询不再被 "experiencing some difficulties" 中断，无人值守跑批
simulate.js显示 Rate Limit 配额（进度条），读 x-ratelimit-limit/remaining；提供"刷新配额"按钮（主动删一次模拟换配额，10 分钟≤5 次）实时掌握剩余并发配额，避免 429 打满；与你的 BatchSize=8 / PipelineDepth=7 联动调度

5. 提交门槛实时看板 → 避免无效矿（background.js: getAlphaCheckStates）

注入的 fetch 拦截器给 alphas 列表自动补 failedNumRA/failedNumPPA/maxProdCorr/maxPoolProdCorr/maxSelfCorr/WQPPYS（命中的 pyramid）。用途：

  • RA/PPA 硬门槛：候选 failedNumRA>0 直接不合格，不因 Sharpe/Fitness 好看而误判（与 brain-alpha-orchestrator 的 failed-gates 规则一致）。
  • WQPPYS（pyramid 匹配）：提交前确认是否命中 MATCHES_PYRAMID——不匹配就是提交死路；命中信息可指导该数据集的字段组合习惯。

6. 社区方法论 AI 辅助阅读（communityAssistant.js + llmService.js）

扩展支持在社区帖子页注入 AI 助手（可自由配置 OpenAI 兼容 LLM），做帖子总结、生成草稿、圈出方法论。对挖掘的价值：快速把社区实战帖（如你记忆中的 ASI_MINVOL1M 方法论帖）转成可执行的字段/参数配方，节省逐帖精读时间。

四、已沉淀的 18 条规则（可复用资产）

此前已把数据包用法沉淀为 webdatascope-data-quality.md 的 18 条规则，并封装成 tools/webdata_quality.py。关键命令：

# 数据集排名 + 甜点区 + OS 退化 + 类别统计 + Universe 覆盖
python tools/webdata_quality.py --zip WebData_20260219_V0.10.9.zip --region USA --delay 1

# 跨区域数据集对比（识别 region-specific 机会）
python tools/webdata_quality.py --zip WebData_20260219_V0.10.9.zip --region ASI --delay 1 --cross-region

# 字段级体检（分布形状解析 + 预处理算子建议 + 字段组合建议）
python tools/webdata_quality.py --zip WebData_20260219_V0.10.9.zip --region USA --delay 1 --fields fundamental6,insiders3

# 挖掘推荐表（综合 sharpe×甜点区×OS质量×中性化可靠度）
python tools/webdata_quality.py --zip WebData_20260219_V0.10.9.zip --region USA --delay 1 --recommend
