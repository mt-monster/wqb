### ★ 降 prod 的两条判据

1. **保序变换改不动 prod**：`ts_rank` prod **0.7519** vs `ts_quantile` prod **0.7512**（差 0.0007 = 噪声）
   ⇒ 真正改排序的量纲只有 `ts_delta`/`ts_rank`/`ts_quantile`/`ts_zscore`/`ts_av_diff`/`ts_ir`，**实际可用 2 类**。
2. **墙密度决定命运**：`[0.6,0.7)` 桶 **n 个位数 = 单钉子可撬**（腿 A：n=9，0.7406→0.6938）；
   **几十以上 = 密墙无解**（腿 B：n=32）。
   ⚠ 且须区分「**新增裁剪**」（有效）与「**裁剪参数微调**」（近乎无效，腿 C 案例）。

### 骨架必须匹配「量的类型」

| 量的类型 | 应有骨架 | 实证 |

# 六 SOP 标准步骤（候选流水线，2026-10-07）

> 任何候选在进入**候选池 / 台账 / 提交队列**之前，按序执行下列**强制**步骤。

| 序 | 步骤 | 判据 | 工具 |
|---|---|---|---|
| 0 | **换手前置判据** ★ | **TO < 0.03 剔除 ｜ TO > 0.70 剔除**；区间内才继续 | `to_prefilter.py` |
| 1 | 发批前四闸 | ① 值型 ② 算子元数 ③ 算子实集合 ④ **平台字段存在性** | dispatch 内置 + `validate_expressions` |
| 2 | 资格门 | RA 全部失败项 = 0（**含 WARNING 类**，IS 层 WARNING 在提交层会升级为 FAIL） | `tools/submit_verdict.py` |
| 3 | 相关性 | **提交前不必本地单独复测 prod**（`prod_gate` 节点会实时拉取，拿不到即 fail-closed）★ 2026-10-08 用户裁定；候选**预先排序**时才需 `check_correlation(refresh=True)`。self < 0.70 用 `check_self_correlation`（本地、不占队列） | 节点内置 `prod_gate` / `check_self_correlation` |
| 4 | 卡点分类 | 按 §五.5.2 三型（A prod 墙 / B 2Y 塌 / C 低于闸线）标注，**C 型保留复访权，不得归入"判死"** | — |

**★ 步骤 3 的裁定理由（2026-10-08）**：提交前的独立 `check_correlation(refresh=True)` 与 `prod_gate` 节点**抢同一个单并发队列**，
反而更易触发 `correlation_busy` 拒发 ⇒ **冗余且有害**。跳过它不降低安全标准（硬闸在节点内）；
遇 `correlation_busy` 只需**间隔重试（≥90s）**，**切勿改参数或降标准**。

**★ 步骤 0 的设立理由**：TO 在回测后即已知，而 prod/self 昂贵且**单并发排队** ⇒
先用零成本判据砍掉结构性不合格项（近乎静态 / 超上限），再做昂贵检查。

**★ 步骤 4 的教训来源**：本战役曾把「S1.66 / F1.00 / 只差 2Y」的 `last_diff_value` 误列入"全灭"，
复查后挂上修复器即成为 **S1.97 / F1.30 / prod 0.6793** 的全闸候选 ⇒ **近似项必须复测，不得一次不过就归档。**
