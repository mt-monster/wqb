## 1. F 公式推导：为什么「只差 S」其实还要看 R

平台 `fitness` 实测符合：

```
F = S × sqrt( |R| / max(TO, 0.125) )
```

本族所有候选的 TO 都在 **1.3%–1.8%**，远低于 12.5% 下限 ⇒ `max(TO, 0.125) = 0.125` 恒成立，于是：

```
F = S × sqrt(R / 0.125)
```

**要同时过 S ≥ 1.58 与 F ≥ 1.0，必须**：

```
sqrt(R / 0.125) ≥ 1.0 / 1.58 = 0.6329
⇒ R ≥ 0.125 × 0.4006 = 5.008%
```

**验证（三条实测，误差 < 0.5% 绝对值）**：

| alpha | S | R | 公式算 F | 实测 F |
|---|---|---|---|---|
| `9qxoORlK` | 1.48 | 5.88% | 1.48 × 0.6859 = 1.015 | **1.02** ✅ |
| `1YNvAPwk` | 1.52 | 4.95% | 1.52 × 0.6293 = 0.957 | **0.96** ✅ |
| `j2YLKx69` | 1.37 | 5.84% | 1.37 × 0.6835 = 0.936 | **0.94** ✅ |

**⇒ 本族的通关条件收敛为两个数字：`S ≥ 1.58` 且 `R ≥ 5.01%`。**

这修正了此前「只差 S」的误判：`1YNvAPwk` 的 S 1.52 只差 3.9%，但 R 4.95% 也差 1.2%，**两个缺口要同时补**。

### 3.2 三条归因

**(a) `bucket` 是三项同时改善的唯一手段**

相比基线：S +2.7%（1.48→1.52）、**SUB/S +6.1%（0.4527→0.4803）**、2Y +15.3%（1.76→2.03）、

| | 1YNvAPwk | 9qxoORlK | gJev5bKJ | j2YLKx69 | 0mYo26wK | xArMpWNl |
|---|---|---|---|---|---|---|
| **1YNvAPwk**（bucket 轴） | 1.00 | **0.6697** | **0.6605** | **0.6599** | **0.6989** | **0.6963** |
| **9qxoORlK**（median） | 0.6697 | 1.00 | **0.9957** | **0.9946** | 0.9856 | 0.9137 |
| **gJev5bKJ**（ceo） | 0.6605 | 0.9957 | 1.00 | 0.9898 | 0.9795 | 0.8994 |

| **xArMpWNl**（zscore） | 0.6963 | 0.9137 | 0.8994 | 0.9283 | 0.9246 | 1.00 |

**读法**：

1. **`ceo ↔ median ↔ max` 三代换聚合口径 = 0.9898–0.9957**。这与记忆里「换字段 ≈ 0.84」的规律**不同且更极端**——因为三者是 `median/max` 对同一底层分布的不同统计量，信息高度重叠。
2. **`subindustry → industry` 换粒度 = 0.9856**。分组粒度不是正交维度。
3. **`bucket(董事会规模)` 对全部 = 0.6599–0.6989**。这是唯一真正换掉分组轴的模板，也是唯一把相关压到 0.70 以下的。
4. **`group_zscore` 版对基线 0.9137** —— 它的低 S 换来了部分分化，但代价太大不划算。
5. `max_mutually_below_subset = [9qxoORlK, 1YNvAPwk]`，**最大互斥子集只有 2 颗**（阈值 0.7）。

**⇒ 点塔缺口结论：要在 `board_gov_stats` 凑 3 颗两两 < 0.7，`bucket` 轴只能贡献 1 颗分化；第 3 颗必须换到别的东西（时间尺度跨度 ≥ 3–4 倍，或换信号族到网络单独 / 姓氏集中 / 学历分布）。**

## 6. 工程故障：prod 一直 pending 的真因是代理挂了

**现象**：`ZYQZbnYx` 连续两轮 prod 全空，累计 307 次查询 / 493 秒，`platform_retry_after=1.0`，日志全为 `status=pending`。

**误判路径**：曾归因为「并行会话抢账号级单并发」→「轮询太密」→「IS alpha 平台还没算」，全错。

**真因**：本机代理 `127.0.0.1:7897` **停止监听**（`Test-NetConnection` 返回 `listening=False`），而 `HTTP_PROXY` / `HTTPS_PROXY` 环境变量仍指向它。日志里其实早有铁证：

```
ProxyError('Unable to connect to proxy',
  NewConnectionError("HTTPSConnection(host='127.0.0.1', port=7897): WinError 10061 目标计算机积极拒绝"))
```

**修法**：跑 `prod_wait.py` 前清空四个代理变量，直连（`GET /authentication` 返回 204 验证通过）：

```powershell
$env:HTTP_PROXY=''; $env:HTTPS_PROXY=''; $env:http_proxy=''; $env:https_proxy=''; $env:NO_PROXY='*'
```

**纪律**：`pending` 类故障排查第一步是**抓 `ProxyError` / 网络层异常**，而不是先怀疑平台侧或并发锁。对照实验（拿已知有值的 alpha 打一次）能区分「平台坏」与「本机网络坏」——本轮是本机坏。
