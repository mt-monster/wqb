## 5. 如何最大化速度 (推荐)

### 推荐: 方案 D (减天 + 减字段) → ~18h

**改法**:
```python
# 改 glb_machine_lib.py:
# 1) ts_factory 天数: [5, 22, 66, 120, 240] → [5, 22, 66]
# 2) field_scan 时取 top 150 fields (按 coverage 降序)
```

**理由**:
- **ts 5,22,66 天** 覆盖了短期(5d动量)、中期(22d趋势)、长周期(66d季度),120/240 天基本是重复信息
- **top 150 字段** (analyst15 共 307 字段)保留覆盖率最高的,丢的是冷门字段
- 一阶到三阶的流水线不会丢 alpha,只是范围缩小

### 可选加速: 间隔 25s → 20s

Token-Bucket 实测: 容量 C=7, refill≈1/30s。当前 25s 间隔安全。
降到 20s 仍在安全区边缘,可考虑;15s 以下有 429 风险(取决于同时段的 V44/V45 负载)。

## 6. 并发模型 — Token-Bucket (实测结论)

经 `probe_concurrency.py` 及多轮实验(实验1-6)精确测定:

| 参数 | 测定值 |
|---|---|
| **瞬时并发上限 C** | **7** (置信区间 6-8, ±1 来自 V44/V45 后台噪声) |
| **令牌补充速率** | **1 令牌 / 20-40 秒** (慢补充) |
| **安全操作包络** | 同时提交 ≤6, 间隔 ≥15-20s |

**模型**:
```
提交 POST /simulations ──► [Token Bucket, C=7, refill≈1/30s]
                          ├─ 接纳(201) ──► 平台排队计算
                          └─ 拒绝(429) ──► 客户端退避重试
```

**关键约束**:
- 瞬时并发提交 ≤ 6 (留 1 余量给 V44/V45)
- 持续提交间隔 ≥ 15-20s (匹配补充速率)
- multi-sim(8表达式/次)与单simulation 均计为 1 个令牌
- **禁止齐射**: ≥8 个提交在 <2s 内并发必现 429
